# PRD: Lexer (tokenizer) for Ofan

> This PRD defined the canonical token set and syntax rules for Ofan, decided across a
> dedicated syntax-design session. Its content has been migrated into
> [`docs/SYNTAX_SPEC.md`](../SYNTAX_SPEC.md), which is now the canonical reference.
> This file is preserved as a historical artifact.

## 1. What is this?

The lexer converts raw `.ofn` source text into a stream of tokens for the parser. This PRD
defines the **canonical token set and syntax rules** for Ofan, decided across a dedicated
syntax-design session, and translates those decisions into concrete lexer requirements.

## 2. Why now?

Per `docs/PROGRESS.md`, the lexer is the next implementation task after the foundational
scaffold. A lexer cannot be written without a settled grammar — this PRD **is** that grammar,
scoped to what the lexer needs (tokens, not full parsing rules).

## 3. Scope

**In scope:**
- Full token inventory: keywords, literals, operators, punctuation, comments
- Identifier and casing rules
- Numeric/string/char literal forms
- Canonical syntax decisions needed to avoid token ambiguity (pillar 3)
- Lexer-level error requirements (pillar 5)

**Explicitly out of scope** (deferred to the parser/typechecker PRDs):
- Grammar/parsing rules (statement structure, expression precedence beyond what's needed to
  tokenize unambiguously)
- Semantic analysis (lifetime inference itself, type checking)
- Any syntax for domains explicitly deferred per `PHILOSOPHY.md` §5 (web, app dev)
- Anything still marked **UNRESOLVED** below — those need their own follow-up decisions
  before the lexer can be considered complete for that token

## 4. Design

### 4.1 Comments
**UNRESOLVED** — not yet decided in this session. Needs explicit decision (single-line `//`,
block `/* */`, doc comments) before lexer is complete. Flagging rather than guessing.

### 4.2 Identifiers & casing
**UNRESOLVED** — not yet decided. Open question: is casing (e.g. `snake_case` for variables)
enforced by the compiler or merely conventional? Pillar 3 implications either way.

### 4.3 Statement termination
**Decided: required semicolons.** Chosen over newline-significant or ASI-style termination.
Rationale: a missing semicolon is a precise, explicit, easily-suggestible parse error
(pillar 5), whereas newline-significance and ASI both introduce a second, implicit grammar
governing where statements end — in tension with pillar 3 (single canonical syntax) and
pillar 1 (explicit, never silent).

### 4.4 Block delimiters
**Decided: braces `{ }`.** Rejected significant whitespace (indentation-as-syntax risks
tooling disagreement about what's canonical — tabs vs. spaces, continuation rules — in
tension with pillar 3) and keyword blocks (`do...end`, slower to type, no speed advantage).

**Decided: braces are mandatory, never optional**, even for single-statement bodies. No
brace-less `if`/loop bodies. Rationale: optional braces create two valid ways to write the
same construct (violates pillar 3) and are a known historical source of silent
structural bugs (e.g. the "goto fail" class of bug) — directly contradicts pillar 1.
One-line brevity is still achievable by placing the brace pair on one line:
`if cond { return x; }`.

### 4.5 Variable declarations
**Decided:**
```ofn
let x: i32 = 5;          // immutable
let mut x: i32 = 5;      // mutable, via modifier — not a separate keyword
const MAX: i32 = 100;    // compile-time constant
```
Only two declaration keywords (`let`, `const`); no third `var` keyword. Mutability is a
modifier (`mut`) rather than a separate keyword, consistent with how `mut` is expected to
apply elsewhere (parameters, references) — one mechanism taught once, not three keywords
teaching overlapping concepts (pillar 3 spirit, pillar 2 ergonomics).

Type annotation is optional when inferable (`let x = 5;`), consistent with treating local
type inference the same way lifetime inference is treated elsewhere in the language.

### 4.6 Function declaration
**Decided:**
```ofn
fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn log_error(msg: &str) {
    print(msg);
}
```
- `fn` keyword (not `func`/`def`) — standard, no learning-curve cost from deviating.
- `->` for return type, explicitly **not** `:`. `:` was tried and rejected — see 4.9.
- No trailing arrow when there is no return value (mirrors `let` having no colon when type
  is inferred — one consistent rule: "annotation appears only when there's something to
  annotate").

### 4.7 Lifetime / region inference and escape hatch
**Decided (core mechanism):** inference is the default and covers the common case
(single input/output borrow relationship) with zero annotation. The escape hatch is a
**plain lowercase word acting as a region tag**, attached to `&`, used only when the
compiler cannot disambiguate which borrows are linked:

```ofn
fn first_word(s: &str) -> &str { ... }                 // pure inference, no tag needed

fn app_name() -> &static str { "Ofan Compiler" }        // 'static-equivalent: a keyword,
                                                          // not a tag — no linking needed

fn longest(a: &r1 str, b: &r1 str) -> &r1 str { ... }    // region tag links 3 positions

fn pick_first(a: &r1 str, b: &r2 str) -> &r1 str { a }   // distinct tags distinguish
                                                          // unrelated lifetimes

struct Parser<r1> {
    source: &r1 str,
    pos: usize,
}
```

Rationale: Rust's `'a` sigil syntax was rejected as exactly the kind of symbol-soup the
"lower learning curve" thesis (pillar 2) is trying to avoid, given annotations should be
rare under inference. A bare word reads as an ordinary identifier rather than introducing a
new sigil-namespace. `&static` is a keyword (intent: "lives for the whole program") and
**does not require a tag**, since it isn't linking two positions — only the cases that
actually require linking distinct borrows need a named tag at all.

**UNRESOLVED:** `<...>` is used both for region tags (`Parser<r1>`) and will be needed for
type generics (`Stack<T>`) — flagged as a possible overload, tentatively accepted as
"the same category of thing" (compile-time parameters) rather than a true ambiguity, but
not formally closed out. Needs explicit confirmation before the lexer treats `<` / `>` as
single-purpose tokens.

### 4.8 Casting
**Decided: keep `as`.**
```ofn
let mean = sum / (values.len() as f64);
```
A `cast<Type>(value)` alternative was proposed and rejected: it would reuse `<...>` for a
third purpose (alongside generics and region tags) while giving up `as`'s left-to-right,
English-readable order ("this value, as this type") for no clear gain. `as` is one keyword,
unambiguous, and already familiar from prior art — no reason found to deviate.

### 4.9 Type annotation colon — resolved overload
**Decided:** `:` is reserved **exclusively** for "a type follows." This applies consistently
to variable declarations, parameter declarations, and — initially proposed, then
reverted — function return types.

**History worth preserving:** `:` was briefly tried for return types too
(`fn f(): i32`), to avoid introducing `->`. This was rejected after review: stacking three
jobs onto one symbol in a single line (`fn add(a: i32, b: i32): i32`) created a real
scannability problem — the reader cannot visually distinguish "param type" colons from
"return type" colons without parsing context, even though each individual use was
unambiguous in isolation. `->` was reinstated specifically because a structurally distinct
glyph lets the reader jump straight to the return type without scanning through parameter
colons first. **Conclusion: this was a density/scannability problem, not a pure keystroke
problem** — worth keeping in mind if future symbol-reuse proposals arise.

### 4.10 Struct literals — `=` vs `:`
**Decided:** struct literal fields use `=`, not `:`, reserving `:` purely for type
declarations and `=` purely for value-binding:
```ofn
Ok(Stats { mean = mean, min = min, max = max })
```
This closes a genuine ambiguity (not just density): `:` in `let x: i32` means "type
follows," but `:` in `Stats { mean: mean }` would mean "value follows" — two different
relationships sharing one symbol. `=` already means "value is being bound" everywhere else
(`let x = 5`), so this is consistency, not novelty.

### 4.11 Type aliasing
**Decided:** `using <Type> as <alias>;` (e.g. `using f64 as f;`). This aliases a **name**,
not a **syntax form**, so it does not conflict with pillar 3 (which governs syntax-level
aliasing, e.g. `fn`/`func` both being legal — not user-defined naming choices, which are an
ordinary language feature, comparable to Rust's `type` alias).

### 4.12 Operators
**Decided — full operator surface confirmed already near-monocharacter; no further
compression pursued.** Arithmetic, comparison, logical, and bitwise operators keep their
standard single-character forms (`+ - * / % < > & | ^ ~ !`); two-character operators
(`+= == != <= >= && || << >>`) are kept because each is a primitive symbol extended by one
of two consistent rules (doubling = logical form of a bitwise op; trailing `=` = comparison
or compound assignment) — compressing these further would break the pattern that makes them
learnable and would collide with the primitive each is built from.

**Decided — error propagation operator `?`:**
```ofn
fn read_config() -> Checked<Config, &str> {
    let raw = read_file("config.ofn")?;
    let parsed = parse(raw)?;
    Ok(parsed)
}
```
Applies to `Checked<T, E>` or `Option<T>`. On failure/absence, immediately returns from the
enclosing function. On success/presence, evaluates to the unwrapped value. This is a
visible, call-site marker of a fallible operation — judged to satisfy pillar 1 (the failure
path is marked, not invisible, unlike e.g. C++ exceptions).

**Decided — fallback operator `?:`:**
```ofn
let timeout = config.timeout ?: 30;
let name = user.nickname ?: user.full_name ?: "anonymous";
```
Applies to `Option<T>` **only** — explicitly **not** valid on `Checked<T, E>`. Pure
expression, never changes control flow (no early return). Left-associative
(`(a ?: b) ?: c`) and short-circuits left-to-right, consistent with `&&`/`||` — the
right-hand operand is only evaluated if the left is absent.

**Rationale for excluding `Checked<T, E>` from `?:`:** allowing a fallback value to silently
discard an `Err` would be exactly the "silent erroneous behavior" pillar 1 prohibits. Pillar
1 requires that discarding an error never be the cheap/fast path — the deliberately slower
`match` remains the only way to supply a fallback for a `Checked` value, by design.

**`?` and `:` are not combined as a C-style ternary.** A `cond ? a : b` form was considered
and rejected: it would overload both `?` (already "propagate") and `:` (already "type
follows") with a third, positionally-dependent meaning — reintroducing the exact class of
bug pillar 3 work elsewhere in this document was meant to eliminate.

### 4.13 Pointers and raw memory (escape hatch for pillar 2, draft)
**Tentative, not fully locked — flagged for the lexer team to treat as provisional:**
```ofn
let x: &i32 = &y;               // safe borrow (locked, see 4.7)
let p: *i32 = raw_ptr();        // raw/unsafe pointer — distinct glyph, deliberately
                                  // separate from borrow syntax
let b: Box<i32> = Box::new(5);  // owning heap pointer — ordinary generic type, no sigil
```
`*` is proposed to be reserved **only** for raw pointers — never reused for multiplication
in a position-dependent way (unlike C, where `*` for "pointer type" vs. "dereference" is a
well-known readability wart). Whether raw-pointer code additionally requires a marked
`unsafe { }` block (as in Rust) is **UNRESOLVED** and used provisionally in exploratory
examples this session; needs its own decision before lexer work treats `unsafe` as a
reserved keyword.

### 4.14 Explicitly deferred / out of scope for this PRD
- Loop syntax (`for`/`while`/`loop` — used informally in examples, never formally decided)
- `match` / pattern matching syntax (used informally, never formally decided)
- `Option<T>` / `Checked<T, E>` exact variant names and definitions (e.g. `Some`/`None`,
  `Ok`/`Err` equivalents) — `Checked` was discussed as a possible pillar-1-flavored rename
  of `Result`, not finalized
- Method receiver syntax (`self` vs `&self` vs `mut self` — raised, not resolved)
- Copy vs. Move semantics (raised, not resolved — directly affects receiver syntax above)
- Trait/interface syntax
- Module/import syntax and path separator (`::` used informally in examples only)
- Enum declaration syntax
- `#[no_runtime]`-style attributes (used informally in one exploratory example only)

These should not block lexer work on the tokens that *are* decided above, but the lexer's
token set will need a follow-up pass once they're resolved — likely worth a second PRD
rather than reopening this one.

## 5. Pillars check

1. **Explicit erroneous behavior, never silent UB:** Yes — mandatory braces (4.4), the
   `?:` / `Checked` exclusion (4.12), and the `*` vs `&` distinction (4.13) are all
   specifically designed to keep failure paths visible.
2. **Lifetime inference with opt-in escape hatch:** Yes — see 4.7. Plain-word region tags
   are the escape hatch; inference is the default.
3. **Single canonical syntax in persisted source:** Yes, with one open item — the `<...>`
   overload (4.7) is not yet formally closed out and should be resolved before declaring
   this pillar fully satisfied.
4. **Single-binary install:** Not applicable to lexer token design.
5. **Error messages with context + suggestion:** Partially — required semicolons (4.3) and
   mandatory braces (4.4) were both chosen specifically because they produce precise,
   suggestible parse errors. Full pillar-5 compliance depends on lexer error-recovery
   implementation, not just token design — should be revisited explicitly during
   implementation, not assumed satisfied by this PRD alone.

## 6. Test plan

- One test per token type in section 4, confirming correct tokenization
- Negative tests for each rejected alternative (e.g. confirm a lone `:` after `)` in a
  function signature is *not* treated as a return-type marker, to guard against
  regressing back to the rejected 4.9 design)
- At least one ambiguous-input test for the unresolved `<...>` overload (4.7), even if it
  currently just documents expected-but-unresolved behavior
- At least one deliberately malformed input per construct, asserting the resulting error
  includes context + a suggestion (pillar 5), per existing project convention
